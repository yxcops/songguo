# Codex Skill 启动台

## 核心定位

为 Codex 桌面客户端创建一组可见、可点击、可回退的 Skill 入口。

这个 Skill 不负责生成图片、发微博、写公众号或抓取内容。它只负责把已经安装或准备安装的 Codex Skills 整理成一个启动台：一个总文件夹、每个 Skill 一个入口文件夹、每个入口一个专属 Codex 对话。

默认只适用于 Codex 客户端。Hermes、Claude Code 或其他命令行智能体没有同样的“项目 + 线程 + 可视化对话入口”结构；如果用户问这些平台，解释边界，不要照搬这个流程。

## 默认判断

- 默认推荐全局安装 Skill，再用启动台项目做可视化入口。
- 启动台入口是使用约定，不是系统锁。其他 Codex 对话仍然可以显式调用同一个全局 Skill。
- 专属对话用于降低误触发和提升可见性，不保证 100% 锁定某一个 Skill。
- 不要把 Skill 文件夹复制到每个入口目录；入口目录只写说明和工作产物。
- 不要写入账号、API key、cookie、token、私有网址、个人目录快照或浏览器登录状态。
- 不要为了创建入口而执行真实发布、真实抓取、真实扣费生成或账号授权。

## 需要确认的输入

如果用户没有说清楚，最多问 1-3 个短问题：

1. 要整理哪些 Skill：技术名、中文名、GitHub 链接或自然语言用途都可以。
2. 入口放在哪里：新建一个专门项目，还是放到已有 Codex 项目下面。
3. 是否需要安装缺失 Skill：如果涉及第三方 Skill，先审查和列清单，再等用户确认。

如果用户已经明确给出位置和 Skill 列表，直接执行，不要反复确认。

## 推荐结构

### 新建专门启动台

适合用户想集中管理一组同类 Skill，例如“宝玉Skill”“图片工具箱”“发布工具箱”。

```text
Codex/workspaces/<启动台名称>/
├── README.md
├── AGENTS.md
├── <入口显示名>/
│   ├── AGENTS.md
│   └── outputs/ 或 drafts/
└── <入口显示名>/
    ├── AGENTS.md
    └── outputs/ 或 drafts/
```

### 放进已有项目

适合用户已经有“工具箱”这类项目，希望新 Skill 直接出现在里面。

```text
<用户指定项目>/
├── <入口显示名>/
│   ├── AGENTS.md
│   └── outputs/ 或 drafts/
└── <入口显示名>/
    ├── AGENTS.md
    └── outputs/ 或 drafts/
```

不要硬编码某台电脑的用户名或绝对路径。先根据当前工作区、用户说明或已有 Codex 目录规则识别目标位置；识别不出来再问。

## 工作流

### 1. 盘点 Skill

把用户给出的项目整理成表格或短清单：

- 入口显示名，例如“文章封面图”。
- Skill 技术名，例如 `baoyu-cover-image`。
- 用途。
- 风险级别：普通、生成消耗、发布账号、非官方抓取。
- 是否已安装。

第三方 Skill 不要盲装。安装前要读 `SKILL.md` 或仓库说明，确认它做什么、会不会调用外部服务、会不会发布内容、是否有明显风险。用户明确确认后再安装。

### 2. 创建入口文件夹

为每个入口创建一个独立文件夹。文件夹名用用户能看懂的显示名，不要强行使用技术名。

普通生成类入口使用：

```text
outputs/
```

发布类入口使用：

```text
drafts/
```

抓取、转换、整理类入口按用户场景选择 `outputs/` 或 `drafts/`。不要覆盖已有文件夹；如果同名入口已存在，先读取现有内容并增量更新。

### 3. 写入口说明

每个入口文件夹写一个 `AGENTS.md`。内容要短，重点写清楚：

- 这个入口默认使用哪个 Skill。
- 用户在这个对话里通常会说什么。
- 默认输出放哪里。
- 哪些事必须先确认。
- 哪些事不要做。

示例：

```md
# 文章封面图

这个入口默认使用 `$baoyu-cover-image`。

用户在这个对话里提出“生成封面图”“做文章封面”“给这篇文章配封面”等请求时，优先按文章封面图流程处理。

默认把产物保存到 `outputs/`。

不要擅自调用发布、抓取、账号登录或扣费批量生成。需要真实生成多张图片、使用外部 API 或调用浏览器账号时，先说明影响并等待确认。
```

发布类入口必须额外写：

```md
默认先生成草稿，不要直接发布。
发布前必须让用户确认账号、内容、图片、时间和平台。
```

非官方抓取类入口必须额外写：

```md
这是非官方方式。执行前必须让用户确认目标链接、用途和是否继续。
```

### 4. 创建专属对话

如果当前 Codex 环境提供线程管理工具，优先为每个入口创建一个 Codex 对话：

- 标题使用入口显示名。
- 工作目录优先指向该入口文件夹。
- 初始提示写明默认使用哪个 Skill，并要求先读取当前文件夹的 `AGENTS.md`。

如果线程工具不能设置子文件夹工作目录，就把对话建在启动台根目录，并在初始提示里明确入口名和 Skill 名。告诉用户这种方式是“软绑定”，不如子文件夹严格。

如果当前环境没有线程管理工具，不要改 Codex 私有数据库。给用户一段手动创建对话的提示词即可。

### 5. 验证

完成后必须检查：

- Skill 是否安装或已列明待安装。
- 入口文件夹数量是否等于 Skill 数量。
- 每个入口是否都有 `AGENTS.md`。
- `AGENTS.md` 是否引用了正确 Skill。
- 发布、抓取、扣费生成类入口是否写了确认规则。
- 新文件里没有账号、API key、token、cookie、密钥、个人登录信息。
- 如果在 Git 仓库里，检查 `git status`，只保留本次应有改动。

建议用这些关键词做隐私检查：

```bash
rg -n "api[_-]?key|secret|token|cookie|authorization|bearer|password|passwd|access[_-]?key|refresh[_-]?token" <目标目录>
```

命中后逐条判断。示例文字可以保留，真实密钥必须删除。

## 输出给用户

结果要讲人话：

- 创建了哪个启动台。
- 放在哪里。
- 有几个入口。
- 哪些 Skill 已安装，哪些只是入口。
- 创建了哪些专属对话。
- 是否发现隐私信息。
- 是否还需要用户确认安装、登录、发布或上传。

如果用户要求“可以上传 GitHub，但先不要上传”，只做到可提交状态。可以检查状态和建议提交内容，但不要 `git push`。
